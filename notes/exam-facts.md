## 02 · Cloud Native Architecture

| Fact | Value | Chapter |
|---|---|---|
| Four goals of cloud native architecture (course framing) | **Application availability, cost management, efficiency, reliability** | [02-01](02-cloud-native-architecture/01-monolithic-vs-microservices.md) |
| Monolithic application | All functionality in a **single deployable unit**; simplest to start, hard to maintain and scale as it grows | [02-01](02-cloud-native-architecture/01-monolithic-vs-microservices.md) |
| Tightly coupled architecture | Components are interdependent — **a change in one component will likely impact other components**; needs coordinated rollouts | [02-01](02-cloud-native-architecture/01-monolithic-vs-microservices.md) |
| Classic monolith layers | User Interface → Business Logic → Data Interface → Database | [02-01](02-cloud-native-architecture/01-monolithic-vs-microservices.md) |
| What the monolith is bound to | Runtime (PHP / Java) + web server (Apache HTTP Server / NGINX); database via an **ODBC** (Open Database Connectivity) driver | [02-01](02-cloud-native-architecture/01-monolithic-vs-microservices.md) |
| Shared-host dependency conflict | Apps installed directly on the OS share one filesystem (`/usr/*`, `/etc/*`) and therefore **one copy of each library**; app2 needs Library XYZ v1.0, app3 needs v2.0 → neither can change independently. This is the host-level problem **containers** solve | [02-01](02-cloud-native-architecture/01-monolithic-vs-microservices.md) |
| Microservices architecture | Application broken into **independent services, each focused on a specific functionality**, communicating over the network | [02-01](02-cloud-native-architecture/01-monolithic-vs-microservices.md) |
| Microservices advantages | Independent **scaling, deployment, technology choice (polyglot), fault isolation, team ownership** | [02-01](02-cloud-native-architecture/01-monolithic-vs-microservices.md) |
| Microservices disadvantage | **Operational overhead** — networking, service discovery, observability, more things to test/deploy/maintain | [02-01](02-cloud-native-architecture/01-monolithic-vs-microservices.md) |
| Ingress (one-liner) | API object managing external access to services in a cluster; **traffic routing is controlled by rules** (path- or host-based) | [02-01](02-cloud-native-architecture/01-monolithic-vs-microservices.md) |
| Data layer in microservices | Per-service data stores; relational scale-out via **replication** and/or **sharding**; shared consistent state via a distributed key/value store | [02-01](02-cloud-native-architecture/01-monolithic-vs-microservices.md) |
| etcd | Distributed, reliable **key/value store**; consistency via the **Raft** consensus algorithm; also the Kubernetes control-plane datastore | [02-01](02-cloud-native-architecture/01-monolithic-vs-microservices.md) |
| Four characteristics of cloud native applications | **Resilience, agility, operability, observability** | [02-02](02-cloud-native-architecture/02-cloud-native-practices.md) |
| Four pillars of cloud native architecture (MCDC) | **Microservices, Containerisation, DevOps, Continuous Delivery** — "Morning Coffee Delivers Caffeine Delight" | [02-02](02-cloud-native-architecture/02-cloud-native-practices.md) |
| Self-healing chain | **Deployment** (declarative desired state + replica count) → **ReplicaSet** (managed by the Deployment; maintains the desired number of Pods) → **Pod** | [02-02](02-cloud-native-architecture/02-cloud-native-practices.md) |
| Pod (one-liner) | **Smallest deployable unit** in Kubernetes; one or more containers with **shared networking and storage**; "think of a Pod as an isolated host" | [02-02](02-cloud-native-architecture/02-cloud-native-practices.md) |
| Which object directly maintains the Pod count? | The **ReplicaSet** (the Deployment manages the ReplicaSet) | [02-02](02-cloud-native-architecture/02-cloud-native-practices.md) |
| Continuous Integration | Every commit automatically **built, unit-tested, integration-tested** | [02-02](02-cloud-native-architecture/02-cloud-native-practices.md) |
| Continuous Delivery | Changes automatically built, tested and made **deployable / released to an acceptance environment**; the production release is a **manual (human) decision** | [02-02](02-cloud-native-architecture/02-cloud-native-practices.md) |
| Continuous Deployment | "Goes a step further" — every passing change goes to **production automatically, no human step**; needs strong automated testing and **rollback** | [02-02](02-cloud-native-architecture/02-cloud-native-practices.md) |
| Bare "CD" / "CI/CD" on the exam | Read as Continuous **Delivery** unless the question says "deployment" or "automatically to production without manual intervention" | [02-02](02-cloud-native-architecture/02-cloud-native-practices.md) |
| Zero trust | "**Never trust, always verify**" — no trust from network location; verify every access, even inside the perimeter; always use **mTLS** between services | [02-02](02-cloud-native-architecture/02-cloud-native-practices.md) |
| mTLS vs TLS | TLS validates **one** side (the server); **mutual** TLS validates **both** sides and encrypts the traffic | [02-02](02-cloud-native-architecture/02-cloud-native-practices.md) |
| Secure by default — the three practices | **Zero trust · secure channels · least privilege** | [02-02](02-cloud-native-architecture/02-cloud-native-practices.md) |
| Secure channel vs zero trust | Secure channel = encryption/integrity of traffic **in transit** (TLS). Zero trust = a **trust model**: identity + authorization verified on every request regardless of location. mTLS is where they overlap | [02-02](02-cloud-native-architecture/02-cloud-native-practices.md) |
| Least privilege | Each identity gets only the permissions its job needs — RBAC, scoped ServiceAccounts, securityContext (non-root, dropped capabilities) | [02-02](02-cloud-native-architecture/02-cloud-native-practices.md) |
| Knative | Kubernetes **serverless** solution providing **scale to zero**; CNCF incubating Mar 2022 → **Graduated Sep 2025** | [02-02](02-cloud-native-architecture/02-cloud-native-practices.md) |
| Serverless (course framing) | Run nothing when there are no requests; scale with demand in both directions; pay only for what is used | [02-02](02-cloud-native-architecture/02-cloud-native-practices.md) |
| Service discovery (definition) | Process of **finding the individual instances that make up a service**; automatic detection, minimal manual configuration | [02-02](02-cloud-native-architecture/02-cloud-native-practices.md) |
| Service discovery in Kubernetes | **Environment variables and DNS**; DNS is preferred; env vars only include Services that **existed before the Pod was created** | [02-02](02-cloud-native-architecture/02-cloud-native-practices.md) |
| Kubernetes Service DNS name | `<service>.<namespace>.svc.cluster.local`, served by CoreDNS | [02-02](02-cloud-native-architecture/02-cloud-native-practices.md) |
| Terraform vs Ansible | Terraform = **infrastructure as code**, declarative provisioning via provider APIs (HashiCorp). Ansible = **configuration management / automation**, procedural playbooks, agentless (Red Hat). Neither is CNCF | [02-02](02-cloud-native-architecture/02-cloud-native-practices.md) |
| Application automation checklist | Speed & agility ✓ · rapid infrastructure + application deployment ✓ · frequent updates ✓ · **manual steps ✗** | [02-02](02-cloud-native-architecture/02-cloud-native-practices.md) |
| Autoscaling (definition) | A pattern for **automatic scaling of infrastructure or application components according to metrics or other requirements** | [02-03](02-cloud-native-architecture/03-autoscaling.md) |
| Automatic vs automated | **Automatic** = works independently; **automated** = a process made independent of human intervention | [02-03](02-cloud-native-architecture/03-autoscaling.md) |
| Three autoscaling triggers | **Reactive** (metric crosses a threshold) · **Scheduled** (known time, e.g. Black Friday) · **Predictive** (AI/ML forecast) | [02-03](02-cloud-native-architecture/03-autoscaling.md) |
| Vertical scaling | Add CPU/RAM/storage to **one machine** ("scaling up"); bare metal has a hard ceiling and steep cost; usually means a **hypervisor** (e.g. VMware ESXi) giving a VM more of its host — capped by what the host has free | [02-03](02-cloud-native-architecture/03-autoscaling.md) |
| Horizontal scaling | **Commodity machines working together as a distributed system**; add/remove resources relative to existing ones ("scaling across"); the cloud native default | [02-03](02-cloud-native-architecture/03-autoscaling.md) |
| Cost of horizontal scaling | Increased **complexity of data sharing** — more instances = more routes and **concurrency**; testing is critical | [02-03](02-cloud-native-architecture/03-autoscaling.md) |
| Cluster Autoscaler | Adjusts the **size of the cluster (nodes)** when Pods **fail to run for insufficient resources** (add) or nodes are **underutilized** and their Pods fit elsewhere (remove) | [02-03](02-cloud-native-architecture/03-autoscaling.md) |
| HorizontalPodAutoscaler (HPA) | **Built in**; scales the **number of replicas** of a Deployment/StatefulSet from CPU/memory (metrics-server) or custom/external metrics | [02-03](02-cloud-native-architecture/03-autoscaling.md) |
| VerticalPodAutoscaler (VPA) | **Add-on** (not shipped with Kubernetes); scales a Pod's **resource requests and limits**; typically restarts the Pod to apply | [02-03](02-cloud-native-architecture/03-autoscaling.md) |
| HPA + VPA together | Don't use both on the same CPU/memory metric for one workload — they conflict | [02-03](02-cloud-native-architecture/03-autoscaling.md) |
| KEDA | **Kubernetes Event-Driven Autoscaling**; CNCF **graduated Aug 2023** (sandbox Mar 2020, incubating Aug 2021); scales on external events via **ScaledObject** triggers; **can scale a Deployment to zero** | [02-03](02-cloud-native-architecture/03-autoscaling.md) |
| KEDA mechanics | Handles **0 → 1** itself; creates and feeds an **HPA** for **1 → n**; scale-to-zero impossible with CPU/memory triggers (nothing to measure) | [02-03](02-cloud-native-architecture/03-autoscaling.md) |
| KEDA trigger examples | Kafka lag, RabbitMQ / AWS SQS / Azure Service Bus queue length, Prometheus query, `cron` (gives scheduled scaling) | [02-03](02-cloud-native-architecture/03-autoscaling.md) |
| Knative vs KEDA | Both reach zero. Knative = serverless **application platform** (request-driven, eventing). KEDA = an **autoscaler** attached to ordinary Deployments | [02-03](02-cloud-native-architecture/03-autoscaling.md) |
| HPA control loop period | Every **15 s** by default (`--horizontal-pod-autoscaler-sync-period` on kube-controller-manager) | [02-03](02-cloud-native-architecture/03-autoscaling.md) |
| HPA formula | `desiredReplicas = ceil(currentReplicas × currentMetricValue / targetMetricValue)`; readings within **10%** of target are ignored | [02-03](02-cloud-native-architecture/03-autoscaling.md) |
| HPA with several metrics | Computes a desired count per metric and uses the **largest** | [02-03](02-cloud-native-architecture/03-autoscaling.md) |
| HPA `Utilization` targets | Usage is a **percentage of the container's resource request** — no request, no metric, no scaling on it | [02-03](02-cloud-native-architecture/03-autoscaling.md) |
| HPA scale-down stabilization | Default **300 s** window before removing Pods; scale-up is immediate | [02-03](02-cloud-native-architecture/03-autoscaling.md) |
| HPA API versions | `autoscaling/v1` = CPU only (what `kubectl autoscale` creates); **`autoscaling/v2`** = memory, multiple metrics, custom/external metrics, `behavior` | [02-03](02-cloud-native-architecture/03-autoscaling.md) |
| What the HPA can target | Anything with a `scale` subresource: Deployment, StatefulSet, ReplicaSet — not a bare Pod or DaemonSet | [02-03](02-cloud-native-architecture/03-autoscaling.md) |
| metrics-server | Add-on that serves the **Metrics API (`metrics.k8s.io`)** from kubelet data; needed by HPA, VPA and `kubectl top`; not installed by default | [02-03](02-cloud-native-architecture/03-autoscaling.md) |
| Serverless (meaning) | **Not** "no servers" — the servers belong to and are managed by the provider; you never choose cores, memory, networking, or patch hardware; you interact via **code or container images** | [02-04](02-cloud-native-architecture/04-serverless.md) |
| Serverless model | **Event → Execution → Billing**; billed for duration (per ms) × memory plus requests; **idle costs nothing** | [02-04](02-cloud-native-architecture/04-serverless.md) |
| FaaS | **Function as a Service** — AWS Lambda is the reference example (also Azure Functions, Google Cloud Functions) | [02-04](02-cloud-native-architecture/04-serverless.md) |
| Lambda deployment packages | Code as a **.zip file** or as a **container image** | [02-04](02-cloud-native-architecture/04-serverless.md) |
| Lambda's four promises | No infrastructure to manage · auto-scales from a dozen events/day to hundreds of thousands/s · pay per ms of compute · tune memory size, **provisioned concurrency** for double-digit ms latency | [02-04](02-cloud-native-architecture/04-serverless.md) |
| Lambda free tier | **1 million requests** free per month | [02-04](02-cloud-native-architecture/04-serverless.md) |
| Cold start | First request to a function with no warm environment: create environment → load runtime + code → run init → handle; hundreds of ms to seconds (JVMs slowest) | [02-04](02-cloud-native-architecture/04-serverless.md) |
| Provisioned concurrency | Execution environments **pre-initialized and kept warm** → no cold start, **double-digit ms**; **billed continuously** even when idle; for latency-sensitive interactive workloads | [02-04](02-cloud-native-architecture/04-serverless.md) |
| Reserved concurrency | A **cap and guarantee** on a function's concurrent executions (protects downstream systems); **free** | [02-04](02-cloud-native-architecture/04-serverless.md) |
| Serverless scaling limits | Native autoscaling from **zero**, bounded by the **account concurrency quota** (Lambda classic default 1,000/Region, soft), function **timeout**, reserved concurrency, and your **budget** — runaway bills are the serverless failure mode | [02-04](02-cloud-native-architecture/04-serverless.md) |
| Kubernetes serverless options (course) | **Knative** and **OpenFaaS** | [02-04](02-cloud-native-architecture/04-serverless.md) |
| Knative Serving | Knative **Service** → URL, immutable **revisions**, **traffic splitting**; autoscaler + **activator** scale revision Pods **0 → n → 0** on in-flight requests | [02-04](02-cloud-native-architecture/04-serverless.md) |
| Knative Eventing | Sources → **Broker + Trigger** → sink, carried as **CloudEvents** | [02-04](02-cloud-native-architecture/04-serverless.md) |
| OpenFaaS | Functions packaged as **OCI images** deployed on Kubernetes; scales to zero; **not a CNCF project** (OpenFaaS Ltd; Community Edition + Pro) | [02-04](02-cloud-native-architecture/04-serverless.md) |
| CloudEvents | CNCF **specification for describing event data in a common way**; **Graduated Jan 2024** (accepted May 2018, incubating Oct 2019); CNCF Serverless Working Group | [02-04](02-cloud-native-architecture/04-serverless.md) |
| CloudEvents required attributes | `id`, `source`, `specversion`, `type` (optional: `time`, `subject`, `datacontenttype`, `dataschema`) | [02-04](02-cloud-native-architecture/04-serverless.md) |
| CloudEvents SDKs / bindings / formats | SDKs: Go, Java, JavaScript, Python, Ruby, Rust, C#, PHP, PowerShell · bindings: **AMQP, HTTP, Kafka, MQTT, NATS, WebSockets** · formats: JSON, Avro, Protobuf, XML | [02-04](02-cloud-native-architecture/04-serverless.md) |
| TOC | **Technical Oversight Committee** — the CNCF's technical governing body: technical vision, **accepts projects and moves them between levels**, aligns interfaces | [02-05](02-cloud-native-architecture/05-community-and-governance.md) |
| TOC composition | **11 members**, two-year staggered terms: **6** elected by the Governing Board, **2** by end users, **1** by project maintainers, **2** by the TOC | [02-05](02-cloud-native-architecture/05-community-and-governance.md) |
| Governing Board (GB) | The **business** body — budget, marketing, trademarks; does *not* approve projects | [02-05](02-cloud-native-architecture/05-community-and-governance.md) |
| End User TAB | End User **Technical Advisory Board** — voice of end users, advisory to the TOC, elects 2 TOC seats | [02-05](02-cloud-native-architecture/05-community-and-governance.md) |
| CNCF maturity levels | **Sandbox → Incubating → Graduated** (+ **Archived** for inactive projects); a *signal to adopters* about which enterprises should adopt | [02-05](02-cloud-native-architecture/05-community-and-governance.md) |
| Maturity ↔ Crossing the Chasm | Sandbox = **Innovators** (techies) · Incubating = **Early adopters** (visionaries) · Graduated = **Early majority** (pragmatists); late majority/laggards have no level. | Editing files inside a container | Changes only that container's **writable layer**: not the image, not other containers, lost on `docker rm`; use a **mount** for content that changes independently of the image | [03-05](03-containers-with-docker/05-networking-and-volumes.md) |

| Read-only mounts | `:ro` with `-v`, `readonly` with `--mount` | [03-05](03-containers-with-docker/05-networking-and-volumes.md) |

| Dockerfile | Text file of instructions `docker build` turns into an image; the first draft is often a `history` transcript of an interactive session | [03-06](03-containers-with-docker/06-building-container-images.md) |

| `USER` | Sets the **user (UID) and optionally group (GID)** for the remainder of the stage and for the running container; the user must exist (`adduser` first); containers run as **root by default** | [03-06](03-containers-with-docker/06-building-container-images.md) |
| `adduser` flags (Alpine) | `adduser -g "Thomas Anderson" -s /usr/sbin/nologin -D -H thomas` — `-g` display name · `-s` no-login shell · `-D` no password · `-H` no home | [03-06](03-containers-with-docker/06-building-container-images.md) |
| `LABEL` | Key=value image metadata; use the **OCI annotation keys** `org.opencontainers.image.authors / description / source / version / revision / licenses / title`; replaces the deprecated **`MAINTAINER`**; several per instruction | [03-06](03-containers-with-docker/06-building-container-images.md) |
| Layer-creating instructions | **`FROM`, `RUN`, `COPY`, `ADD`**; everything else (`WORKDIR`, `ENV`, `LABEL`, `EXPOSE`, `USER`, `CMD`, `ENTRYPOINT`, …) is metadata | [03-06](03-containers-with-docker/06-building-container-images.md) |
| Reducing layers | Chain commands in **one `RUN` with `&&`** and `\` continuations; combine package-index update and install in the same instruction (a separate cached `update` layer goes stale); `apk add --no-cache` / clean caches in the same layer | [03-06](03-containers-with-docker/06-building-container-images.md) |
| Multi-stage build | Multiple `FROM`s in one Dockerfile; **`FROM base AS name`**; **`COPY --from=name src dst`** copies artifacts between stages (or from any image); **the last stage is the output**; `--target` builds an earlier stage. Introduced Docker **17.05**; replaces the two-Dockerfile 'builder pattern' | [03-06](03-containers-with-docker/06-building-container-images.md) |
| Why multi-stage | **Build tools, headers and source stay in a discarded stage**; the runtime image holds only the artifact and its runtime deps → smaller, fewer CVEs, nothing to leak | [03-06](03-containers-with-docker/06-building-container-images.md) |
| Static linking vs runtime data | `LDFLAGS="-static"` bundles libraries into the binary, but **data files** (ncurses' terminfo database) must still be installed — `ncurses-terminfo-base` | [03-06](03-containers-with-docker/06-building-container-images.md) |
| Build cache | Layers are cached while the instruction **and everything before it** are unchanged; order **least → most frequently changing** (base, packages, dependency manifests, source); `--no-cache` rebuilds all, `--pull` refreshes the base | [03-06](03-containers-with-docker/06-building-container-images.md) |
| `.dockerignore` | Excludes files from the **build context** (the directory sent to the daemon); same syntax as `.gitignore` | [03-06](03-containers-with-docker/06-building-container-images.md) |
| Best practices (Docker) | Multi-stage · small official pinned base · one concern per container · no unnecessary packages · sort multi-line args · exec form · `ENTRYPOINT` + `CMD` · non-root `USER` · `LABEL`s · rebuild often | [03-06](03-containers-with-docker/06-building-container-images.md) |
| Multi-platform image | One tag → an **index (manifest list)** with a manifest per `os/arch`; hosts pull their own variant; an arm64-only image on amd64 fails with **`exec format error`** | [03-06](03-containers-with-docker/06-building-container-images.md) |
| `docker buildx build --platform` | `docker buildx build --platform linux/amd64,linux/arm64 -t user/app --push .`; needs a **docker-container builder** (`docker buildx create --use`) or the containerd image store; **`--push` required** because the classic store can't hold an index | [03-06](03-containers-with-docker/06-building-container-images.md) |
| Multi-platform strategies | **QEMU emulation** (binfmt_misc; no Dockerfile changes, slow) · **multiple native nodes** (fast, needs hardware) · **cross-compilation** (`$BUILDPLATFORM` / `$TARGETPLATFORM`; language-specific) | [03-06](03-containers-with-docker/06-building-container-images.md) |
| Pushing to a registry | `docker login` → `docker tag IMG user/repo:tag` → `docker push user/repo:tag`; only layers the registry lacks are uploaded; push prints the **digest**; extra tags are free pointers | [03-06](03-containers-with-docker/06-building-container-images.md) |
| Alpine Linux | ~8 MB base image with `apk` and **musl libc**; the usual choice when size matters; `apk add --no-cache pkg` | [03-06](03-containers-with-docker/06-building-container-images.md) |

| `kubectl exec` syntax | **`kubectl exec -it <pod> -c <container> -- <command>`** — everything after `--` is the container's; `-i` keeps stdin open and `-t` allocates a TTY (both needed for a shell); `-c` required for multi-container Pods. `kubectl exec <pod> -- env` prints the environment the container sees | [04-03](04-kubernetes-fundamentals/03-troubleshooting-pods.md) |
| `kubectl debug` | Attaches an **ephemeral container** with your tools to a running Pod — the answer when the image has no shell (distroless/scratch) and `exec` reports `executable file not found` | [04-03](04-kubernetes-fundamentals/03-troubleshooting-pods.md) |
| `kubectl replace --force --grace-period=0` | **Deletes and recreates** the object instead of patching it — most of a Pod's spec is **immutable**, so this is how a Pod's image or command is changed in a lab. `--grace-period=0` skips the 30s termination wait | [04-03](04-kubernetes-fundamentals/03-troubleshooting-pods.md) |

| DaemonSet — definition | **Ensures that all (or some) Nodes run a copy of a Pod.** **Nodes added → Pods added; nodes removed → Pods garbage collected; deleting the DaemonSet cleans up its Pods.** Provides **node-local facilities** | [04-06](04-kubernetes-fundamentals/06-daemonsets.md) |
| DaemonSet has no `replicas` | **There is no `replicas` field in a DaemonSet spec.** The Pod count is an **output** — however many eligible nodes exist. "Scale the DaemonSet" is a distractor | [04-06](04-kubernetes-fundamentals/06-daemonsets.md) |
| Deployment vs DaemonSet | **Deployment = you control HOW MANY replicas** (stateless apps, scaling and rollouts matter more than placement). **DaemonSet = you control NODE COVERAGE** (a copy must run on all or certain hosts because it provides node-level functionality other Pods depend on) | [04-06](04-kubernetes-fundamentals/06-daemonsets.md) |
| Why extra replicas are not coverage | The scheduler **spreads by preference, not guarantee** — 3 replicas on 3 nodes can land **2 + 1 + 0**. And adding a node later changes nothing, because the desired state was a number and it is still satisfied | [04-06](04-kubernetes-fundamentals/06-daemonsets.md) |
| The three workload controllers | **Deployment** — stateless, interchangeable Pods · **StatefulSet** — stable identity and per-Pod storage (databases, clustered systems) · **DaemonSet** — one Pod per node for node-local functionality | [04-06](04-kubernetes-fundamentals/06-daemonsets.md) |
| Typical DaemonSets | **CNI agents** (calico-node, Cilium, Flannel) and **kube-proxy** · **log collectors** (Fluentd, Fluent Bit, Filebeat) · **node metrics** (Prometheus node-exporter, OTel Collector agent) · **CSI node plugins** · security agents (Falco) | [04-06](04-kubernetes-fundamentals/06-daemonsets.md) |
| No `kubectl create daemonset` | The subcommand **does not exist**. Generate a Deployment with `--dry-run=client -o yaml` and change three things: **`kind: DaemonSet`**, **delete `spec.replicas`**, **delete `spec.strategy`** (or replace it with `spec.updateStrategy`). `apiVersion` stays **`apps/v1`** | [04-06](04-kubernetes-fundamentals/06-daemonsets.md) |
| DaemonSet Pod naming | **`<daemonset-name>-<id>`** (e.g. `logger-5jm78`), versus a Deployment's **`<name>-<replicaset-id>-<id>`** — because a **DaemonSet owns its Pods directly**, with **no ReplicaSet in between**, so there is no `pod-template-hash` segment. History is kept in **ControllerRevision** objects instead | [04-06](04-kubernetes-fundamentals/06-daemonsets.md) |
| Downward API for the node name | `env: [{name: NODE_NAME, valueFrom: {fieldRef: {fieldPath: spec.nodeName}}}]` — exposes a field of the Pod's own spec as an environment variable; the standard way to prove DaemonSet coverage | [04-06](04-kubernetes-fundamentals/06-daemonsets.md) |
| How Daemon Pods are scheduled | The controller creates a Pod per **eligible** node and sets **`spec.affinity.nodeAffinity`** to match it; the **default scheduler** then binds it by setting `.spec.nodeName`. A DaemonSet **works within scheduling, it does not override it** | [04-06](04-kubernetes-fundamentals/06-daemonsets.md) |
| DaemonSet automatic tolerations | Added by the controller to every DaemonSet Pod: **`not-ready`** and **`unreachable`** (NoExecute) · **`disk-pressure`**, **`memory-pressure`**, **`pid-pressure`**, **`unschedulable`** (NoSchedule) · **`network-unavailable`** (NoSchedule, **only with `hostNetwork: true`**) | [04-06](04-kubernetes-fundamentals/06-daemonsets.md) |
| Why not-ready/unreachable are tolerated | To break a deadlock: without them a node is never Ready because the **network plugin is not running**, and the network plugin never runs because the **node is not Ready** | [04-06](04-kubernetes-fundamentals/06-daemonsets.md) |
| Control-plane taint | **`node-role.kubernetes.io/control-plane:NoSchedule`** — applied by **kubeadm** to restrict placing Pods on control-plane nodes. Remove with `kubectl taint nodes <node> node-role.kubernetes.io/control-plane:NoSchedule-` (the **trailing `-`** removes a taint) | [04-06](04-kubernetes-fundamentals/06-daemonsets.md) |
| Why a DaemonSet skips the control plane | **The control-plane taint is NOT in the automatic toleration list**, so a plain DaemonSet covers workers only. **kube-proxy and CNI agents run there because they declare the toleration themselves** (often a bare `- operator: Exists`, which tolerates every taint). **k3s does not taint its server node**, which is why the same manifest gives full coverage there | [04-06](04-kubernetes-fundamentals/06-daemonsets.md) |
| Missing DaemonSet Pod — causes | A **taint** with no matching toleration (most common) · a **`nodeSelector`/affinity** the node does not match · **insufficient resources** (`FailedScheduling` in `kubectl describe pod`) | [04-06](04-kubernetes-fundamentals/06-daemonsets.md) |
| Running on a subset of nodes | Set **`.spec.template.spec.nodeSelector`** or **`.spec.template.spec.affinity`**; with neither, Pods go on **all** nodes. **Change node labels and the DaemonSet promptly adds Pods to newly matching nodes and deletes them from newly non-matching ones** | [04-06](04-kubernetes-fundamentals/06-daemonsets.md) |
| DaemonSet update strategy | **`updateStrategy.type`: `RollingUpdate` (default) or `OnDelete`** (new Pods appear only when you delete the old ones). **`maxUnavailable` defaults to `1`** and **`maxSurge` to `0`** — far more conservative than a Deployment's 25%/25%. `revisionHistoryLimit` **10**, `minReadySeconds` **0** | [04-06](04-kubernetes-fundamentals/06-daemonsets.md) |
| `kubectl get daemonset` columns | **`DESIRED`** = nodes that **should** run the Pod (the **eligible node count**) · `CURRENT` running at least one · `READY` · `UP-TO-DATE` on the latest template · `AVAILABLE` · **`NODE SELECTOR`**. `numberMisscheduled` counts Pods on nodes that should not have them | [04-06](04-kubernetes-fundamentals/06-daemonsets.md) |

| `kubectl set image` syntax | **`kubectl set image <type>/<name> <CONTAINER-NAME>=<image>[:tag]`** — the left of the `=` is the **container name from the pod template**, which often differs from the resource name. Works on pod, rc, deployment, daemonset, statefulset, cronjob, replicaset | [04-07](04-kubernetes-fundamentals/07-set-image-and-patch.md) |
| The `*` wildcard in `set image` | **Sets EVERY container in the resource to that one image** — the docs' own example comment is "update image of all containers". Safe for single-container workloads; on a multi-container Pod it overwrites the sidecar too. Name them individually instead: `nginx=... sidecar=...` | [04-07](04-kubernetes-fundamentals/07-set-image-and-patch.md) |
| `set image` on a Deployment vs a Pod | **Deployment**: changes `.spec.template` → **new ReplicaSet, new revision, rolling update**, every Pod replaced. **Bare Pod**: changes `spec.containers[].image` → the kubelet **restarts that container in place**; same Pod, **same IP**, `RESTARTS` increments, **no revision** | [04-07](04-kubernetes-fundamentals/07-set-image-and-patch.md) |
| Mutable Pod fields | Pod updates **may not change fields other than** `spec.containers[*].image`, `spec.initContainers[*].image`, `spec.activeDeadlineSeconds`, `spec.terminationGracePeriodSeconds`, `spec.tolerations` (**additions only**) and `spec.schedulingGates`. Container resources go through the **`resize` subresource** | [04-07](04-kubernetes-fundamentals/07-set-image-and-patch.md) |
| `kubectl set` family | Not just images: **`set image`, `set resources`, `set env`, `set serviceaccount`, `set selector`, `set subject`** — thin wrappers that build a patch for you | [04-07](04-kubernetes-fundamentals/07-set-image-and-patch.md) |
| `set image --local` | **`--local -o yaml`** edits a FILE and never contacts the API server; `--all` hits every resource of the listed types, `-l` selects by label | [04-07](04-kubernetes-fundamentals/07-set-image-and-patch.md) |
| Verifying an image change | `kubectl rollout status` (did it finish) · `kubectl get deploy -o wide` (what the **spec** says) · `kubectl get pods -o jsonpath='{..image}'` (what is **actually running**). A rollout stuck on `ImagePullBackOff` still shows the new image in the spec | [04-07](04-kubernetes-fundamentals/07-set-image-and-patch.md) |
| `kubectl patch` — the three types | **`strategic`** (the **default**) · **`merge`** (RFC 7386 JSON merge patch) · **`json`** (RFC 6902 JSON Patch). Those are the only three values of `--type`. **JSON and YAML are both accepted** as the patch body | [04-07](04-kubernetes-fundamentals/07-set-image-and-patch.md) |
| Strategic merge patch | **Kubernetes' own extension** — the API server knows each list's **merge key** and merges entries by it, so other list entries survive. **Not supported on custom resources (CRDs)** | [04-07](04-kubernetes-fundamentals/07-set-image-and-patch.md) |
| Strategic merge keys | **`containers`, `initContainers`, `ephemeralContainers`, `volumes`, `env`, `imagePullSecrets` → `name`** · **`ports` (container) → `containerPort`** · **a Service's `ports` → `port`**. The docs: "spec.containers[*].name is required because it's a merge key" | [04-07](04-kubernetes-fundamentals/07-set-image-and-patch.md) |
| JSON merge patch (RFC 7386) | Plain JSON semantics, **no schema awareness: arrays are REPLACED wholesale**, so patching one container deletes the others. Its unique trick: **setting a key to `null` deletes it**. Use on CRDs and flat fields | [04-07](04-kubernetes-fundamentals/07-set-image-and-patch.md) |
| JSON Patch (RFC 6902) | A **list of operations**, not a shape of the object. Ops: **`add`, `remove`, `replace`, `copy`, `move`, `test`**. **Atomic** — if one op fails, none apply, which is what makes `test` a useful guard for positional edits | [04-07](04-kubernetes-fundamentals/07-set-image-and-patch.md) |
| What only JSON Patch can do | **Remove a field** (`op: remove`) and **append to a list** (path ending in **`/-`** with `op: add`) | [04-07](04-kubernetes-fundamentals/07-set-image-and-patch.md) |
| JSON Pointer path rules | Slash-separated keys from the root; list elements by **zero-based index**. **`-` means append to the end** (a number inserts *before* that index). **`~1` escapes a literal `/`** and **`~0` a literal `~`** — e.g. `/metadata/annotations/kubernetes.io~1change-cause` | [04-07](04-kubernetes-fundamentals/07-set-image-and-patch.md) |
| Two specs in a row | On a **Deployment** the container image is `/spec/template/spec/containers/0/image`; on a **bare Pod** it is `/spec/containers/0/image`. A patch written for one fails on the other | [04-07](04-kubernetes-fundamentals/07-set-image-and-patch.md) |
| Patching a Deployment | **Changes to the Pods must go through `spec.template`** — that is what updates the ReplicaSet and triggers a rollout. Patching **`spec.replicas` scales with no new revision**; `spec.strategy`/`revisionHistoryLimit`/`paused` change behaviour with no rollout | [04-07](04-kubernetes-fundamentals/07-set-image-and-patch.md) |
| Patch files accept YAML | `kubectl patch` converts its patch input from **YAML to JSON before** it reads `--type`, so **a JSON 6902 patch can be written as a YAML list** and passed with `--patch-file`. No `yq` required — `yq -o=json -I=0` is only for producing a one-liner | [04-07](04-kubernetes-fundamentals/07-set-image-and-patch.md) |
| `--subresource=scale` | `kubectl patch deployment web --subresource=scale --type=merge -p '{"spec":{"replicas":2}}'` — scales through the scale subresource instead of the main spec | [04-07](04-kubernetes-fundamentals/07-set-image-and-patch.md) |

| Service — what it solves | **Pod IPs are ephemeral.** A Service is a **stable name and stable virtual IP** in front of a changing set of Pods — "a single outward-facing endpoint even when the workload is split across multiple backends" | [04-08](04-kubernetes-fundamentals/08-services.md) |
| There are FOUR Service types | **`ClusterIP`** · **`NodePort`** · **`LoadBalancer`** · **`ExternalName`**. `kubectl create service` has exactly those four subcommands. **Headless is NOT a fifth type** (it is `type: ClusterIP` with `clusterIP: None`) and **Ingress is not a Service type at all** | [04-08](04-kubernetes-fundamentals/08-services.md) |
| Ingress vs Services | **Ingress is an Application Service, not one of the core four** — it exposes **HTTP and HTTPS routes from outside the cluster to Services within it**, sitting in front of them. Needs an **ingress controller** to do anything | [04-08](04-kubernetes-fundamentals/08-services.md) |
| `ClusterIP` | **The DEFAULT.** Exposes the Service on a **cluster-internal IP — only reachable from within the cluster**. For internal components like APIs and databases. Expose it externally with an Ingress or Gateway | [04-08](04-kubernetes-fundamentals/08-services.md) |
| `NodePort` | Exposes the Service on **each Node's IP at a static port**; **every node listens**, whether or not it runs a backing Pod. Port range **30000-32767** (`--service-node-port-range`). **Kubernetes also sets up a ClusterIP**, as if you had asked for one | [04-08](04-kubernetes-fundamentals/08-services.md) |
| `PORT(S) 80:32610/TCP` | **First number = the SERVICE port. Second = the NODE port.** Seen on NodePort and LoadBalancer Services | [04-08](04-kubernetes-fundamentals/08-services.md) |
| `LoadBalancer` | Exposes the Service externally **using an external load balancer**. **Kubernetes does not offer a load balancing component — you must provide one** or integrate with a cloud provider. No provider → **`EXTERNAL-IP` stays `<pending>`**. Provisioned by the **cloud-controller-manager**'s service controller | [04-08](04-kubernetes-fundamentals/08-services.md) |
| `ExternalName` | Maps the Service to the contents of **`spec.externalName`**; the cluster DNS returns a **CNAME** with that hostname. **No proxying of any kind** — redirection happens **at the DNS level**. No ClusterIP, no selector, no endpoints, no kube-proxy | [04-08](04-kubernetes-fundamentals/08-services.md) |
| ExternalName caveats | **HTTP/HTTPS are awkward** — the client's hostname differs from the CNAME target, so `Host:` headers and TLS certificates may not match. **It cannot take an IP address** (a digits-only name will not resolve) — use a headless Service for that | [04-08](04-kubernetes-fundamentals/08-services.md) |
| The types stack | A **NodePort Service also gets a ClusterIP**; a **LoadBalancer also gets a node port**. The outer types allocate the inner ones — they are not alternatives | [04-08](04-kubernetes-fundamentals/08-services.md) |
| The three ports | **`port`** = the **Service's** port (what clients connect to) · **`targetPort`** = the **container's** port (defaults to `port`; can be a **named** port from the Pod spec) · **`nodePort`** = the **node's** port (NodePort/LoadBalancer only) | [04-08](04-kubernetes-fundamentals/08-services.md) |
| How a Service finds Pods | **By label selector on Pods** — a Service has no knowledge of Deployments. `kubectl expose deployment/x` copies the Deployment's `matchLabels` into the Service's `spec.selector` and the container port into `port`/`targetPort` | [04-08](04-kubernetes-fundamentals/08-services.md) |
| Endpoints | An object with the **same name as the Service**, holding the **IP:port of every READY Pod** matching the selector. Shown by `kubectl get endpoints` and in `kubectl describe service`. **An empty endpoints list means no backends** — the first check when a Service returns nothing | [04-08](04-kubernetes-fundamentals/08-services.md) |
| EndpointSlice | The chain is **Service → EndpointSlice → Pod**. **Stable since v1.21**; a new slice per **100** endpoints; supports dual-stack. The legacy **Endpoints API was deprecated in v1.33** and **truncates at 1000** endpoints (annotation `endpoints.kubernetes.io/over-capacity: truncated`) | [04-08](04-kubernetes-fundamentals/08-services.md) |
| Headless Service | **`clusterIP: None`** with `type: ClusterIP`. **No cluster IP is allocated, kube-proxy does not handle it, and there is no load balancing or proxying by the platform.** With a selector, DNS returns **A/AAAA records pointing directly at the Pods** | [04-08](04-kubernetes-fundamentals/08-services.md) |
| Why headless still looks load balanced | DNS returns **several A records** and the **resolver** picks one, so repeated `curl` hits different Pods. That is **client-side**, not kube-proxy: a client that resolves once and pools connections **pins itself to one Pod** | [04-08](04-kubernetes-fundamentals/08-services.md) |
| Headless per-Pod DNS names | `<hostname>.<subdomain>.<ns>.svc.cluster.local` — served when a **headless Service exists with the same name as the Pod's `spec.subdomain`**. A **StatefulSet sets `hostname`/`subdomain` automatically** from `spec.serviceName`, giving `web-0.nginx.default.svc.cluster.local`. A plain Deployment does not, so you only get the flat list | [04-08](04-kubernetes-fundamentals/08-services.md) |
| Service DNS name | **`<service>.<namespace>.svc.cluster.local`**. Short name works **within** the namespace; **`<service>.<namespace>`** across namespaces. Driven by the `search` list in the Pod's `/etc/resolv.conf` plus `options ndots:5` | [04-08](04-kubernetes-fundamentals/08-services.md) |
| SRV records | For **named** ports: `_<port-name>._<protocol>.<service>.<ns>.svc.cluster.local` returns the port number as well as the address | [04-08](04-kubernetes-fundamentals/08-services.md) |
| Environment-variable discovery | The kubelet injects `<SVC>_SERVICE_HOST` / `<SVC>_SERVICE_PORT` — but **only for Services that existed before the Pod started**. DNS has no ordering problem, which is why it is preferred | [04-08](04-kubernetes-fundamentals/08-services.md) |
| Throwaway test Pod | **`kubectl run -it --rm curl --image=curlimages/curl --restart=Never -- sh`** — a shell on the Pod network for `curl`, `nslookup` and `/etc/resolv.conf`; `--rm` deletes it on exit | [04-08](04-kubernetes-fundamentals/08-services.md) |
